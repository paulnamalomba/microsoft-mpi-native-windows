Debug-configuration fail-fast: root cause and fix (toward 10.1.4.1)
===================================================================

Version progression: none (10.1.4.0; counter 0 -> 0).

- Symptom: Debug smpd.exe exited at startup with 0xC0000409 and printed
  nothing, so mpiexec reported "unable to start the local smpd manager".
  Release was unaffected.
- Diagnosis: native/tools/crashstack.py (new) runs a program under the Win32
  debug API (DEBUG_ONLY_THIS_PROCESS). It stops at the first fatal event and
  walks the stack with System32 dbghelp and the build's PDBs. No debugger
  install was needed, and the pinned SDK was not changed. Result:
  second-chance 0xC0000409 with fast-fail code 10,
  FAST_FAIL_GUARD_ICALL_CHECK_FAILURE (a Control Flow Guard indirect-call
  check), raised for smpd.exe RVA 0x6cd88 = _initterm+0x58
  (ucrt/startup/initterm.cpp:22), the CRT loop that calls static
  initializers.
- Root cause: the phase 4 hardening change. Upstream compiles with
  ControlFlowGuard (/guard:cf) only in Release (src/mpi.props). The native
  ItemDefinitionGroup that adds /guard:exportsuppress to mpiexec.vcxproj and
  smpd.vcxproj applied to every configuration, and that linker option turns
  CFG on. Debug therefore linked a CFG image from objects compiled without
  /guard:cf. Their static initializers were not registered as valid call
  targets, so the CFG-instrumented CRT _initterm failed fast on the first
  one.
- Fix: the ItemDefinitionGroup condition is now MSMPI_NATIVE == true and
  Configuration == Release, with the reason recorded in each project file.
  Release guard flags stay 0x1001F500, matching Microsoft. Debug images now
  have no CFG, as upstream's Debug configuration intends.
- Observed, unchanged: upstream Debug compiles with /MT and /D _DEBUG
  (mpi.props sets RuntimeLibrary MultiThreaded for every configuration)
  while linking the debug CRT libraries (CRT_Libs libucrtd, libcmtd,
  libvcruntimed). That is upstream's configuration, and it builds and runs.
- Regression check: native/verify.py adds a required Debug stage
  (--debug-build, default out/Debug-x64/bin). It stages the Debug runtime
  and requires VERSIONINFO with VS_FF_DEBUG. It builds the C and Fortran
  probes against the Debug SDK and runs them at 1, 2 and 4 ranks. ProbeChecks()
  now serves both configurations.
- Results: Debug baseline 20261017T050743Z 22/22. crashstack on Debug
  smpd -d 3: no fatal event within 8 s ("smpd listening on port 8677").
  Release baseline 22/22. verify 20261017T051009Z 28/28. check_abi exit 0.

ndutil built from pinned NetworkDirect source (toward 10.1.4.1)
================================================================

Version progression: none (10.1.4.0; counter 0 -> 0).

- Reason: the NetworkDirect 2.0.1 NuGet ndutil.lib holds three 2018 /GL
  (LTCG) objects (dumpbin: ANON OBJECT, 2018-11-06) without a PDB
  (LNK4099). Microsoft documents /GL objects as incompatible across toolset
  versions, even minor updates (C1047). The 14.44 link accepted them, but
  that mix sits outside Microsoft's compatibility guarantee.
- Source pin (native/package-pins.json schema 2):
  microsoft/NetworkDirect 043f1bf05e41343cc88dda619ddd86aee60a02fe
  (2022-08-17, MIT). Per-file SHA-256 pins for LICENSE.txt and the 15
  src/ndutil files. The codeload archive is not pinned, because GitHub may
  regenerate archive bytes; the observed hash is recorded (ca44d828...).
  The NuGet package is now a superseded, SHA-512-verified comparison
  reference only.
- native/build.py:
  - SourceTree() extracts only the pinned files and verifies each.
  - NetworkDirect() runs mc.exe on ndstatus.mc and stages nddef.h,
    ndioctl.h, ndspi.h, ndsupport.h and ndstatus.h. It compiles ndaddr.cpp
    (/Yc precomp.h), ndfrmwrk.cpp and ndprov.cpp (/Yu) with cl /W3 /EHsc
    /GS /sdl /GR- /Gy /MT /Zl /Zi /D _LIB. Release adds /O2 /Oi /GL
    /guard:cf /D NDEBUG; Debug adds /Od /D _DEBUG. lib.exe (/LTCG in
    Release) writes out/<cfg>-x64/networkdirect/lib/ndutil.lib and its PDB.
  - SupersededNuget() and PublicSymbolDifferences() fail the build unless
    ndstatus.h equals the NuGet copy and, in Release, the public symbols
    match. Two name classes that carry no interface are ignored: the
    build-path precompiled-header marker and the newer string-literal
    decoration.
  - Packages() maps a provider 'source' package to its targets file.
    Baseline passes MsmpiNetworkDirectRoot.
- native/networkdirect.targets replaces the NuGet targets for mpichannels,
  mpid and msmpi: include directory plus the source-built ndutil.lib.
- Header identity: NuGet 2.0.1 nddef.h, ndioctl.h, ndspi.h and ndsupport.h
  are byte-identical (CRLF-normalized) to the source commit's, and the
  generated ndstatus.h equals the NuGet copy.
- Symbol parity: /sdl and /GR- were added after the first comparison showed
  the NuGet objects carry __autoclassinit2 members and no RTTI descriptors.
  Final: 128 public symbols on each side, with no differences beyond the
  two ignored classes.
- Results:
  - Release baseline 20261017T051424Z 22/22: the msmpi link uses
    out\Release-x64\networkdirect\lib\ndutil.lib with no networkdirect.2.0.1
    path and no LNK4099; mpichannels compiles against the staged headers.
  - Debug baseline 22/22.
  - verify 20261017T051745Z 28/28.
  - check_abi exit 0; check_errmsgs exit 0.
- Limit: no RDMA hardware or NetworkDirect provider is installed, so the
  NetworkDirect transport itself is untested.
