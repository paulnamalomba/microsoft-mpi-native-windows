Observed Upstream Build System (to be ported)
=============================================

- 21 `.vcxproj` projects driven by `dirs.proj`, using the 2017 CommonBuildToolSet
  (`.build/CBT`, NuGet restore with .NET desktop workloads).
  `Directory.Build.props` pins `PlatformToolset v141`, `VCToolsVersion
  14.15.26726` and `WindowsTargetPlatformVersion 10.0.16299.0`. Upstream's README
  also requires the Windows WDK.
- Fortran interfaces: `src/mpi/msmpi/fortran/lib/mpifort.vcxproj` runs
  `$(GFORTRAN_BIN)\gfortran.exe`, with `GFORTRAN_BIN` set to a mingw-w64
  8.1.0 path in `Directory.Build.props:112`. MinGW is excluded, so the port must
  build these interfaces with the pinned Intel `ifx` and keep the consumer
  ABI (`msmpifec`, `msmpifmc`, modules) compatible.
- Error-message generation: `src/mpi/common/mpicommon.vcxproj:94` runs
  `perl $(MPI_SRC_ROOT)\common\extracterrmsgs`. Strawberry Perl is
  MinGW-based and excluded. The port needs a native Perl or an equivalent
  Python generator with byte-identical output.
- Components: `src/mpi/msmpi/*` (DLL, API, channels, MPID, IO, Fortran),
  `src/mpi/mpiexec`, `src/mpi/smpd`, `src/mpi/pmilib`, `src/mpi/stub` and
  `src/launchSvc`.

Defect Driving The Fork
=======================

- Launch race (Observed): SESKA backend hosted run 38937044789,
  `windows (opt)`, case `displacement-4-mumps`. With `mpiexec -debug 3`, the
  manager logs `ERROR: rejecting unknown process id 3 trying to connect.`
  right after `CreateProcess` of rank 0 (`PMI_SMPD_KEY=3`). The job is then
  aborted ("process exited without calling init"); RPC 1726 on teardown is
  only a consequence.
- Source: `gle_create_mpi_process()` calls `ResumeThread(pi.hThread)`
  (`src/mpi/smpd/smpd_launch_process.cpp:868`) and only after it returns
  does the launch loop call `smpd_add_process(process)` (`:1338`). A rank
  that reaches its PMI connect in that window fails
  `smpd_find_process_by_id()` (`src/mpi/pmilib/SmpdMgrRpcSrv.cpp:439-445`).
- Conditions: oversubscribed two-vCPU Windows Server 2022 runners, where
  the launching thread competes with already-started ranks that busy-poll in
  `MPI_Init`. 600 launches on a Windows 11 desktop (2 and 1 CPUs, 4 and 8
  ranks, busy loops) did not reproduce it; a Server-like long-quantum A/B
  test is in progress in the suite.
- Staged remedy chosen by the user: (1) below-normal rank priority in the
  SESKA launcher and CI now; (2) fix the ordering here (register before
  resume), with a deterministic regression test, and ship this fork's runtime
  app-locally.

Remaining Work
==============

1. Port the build to the pinned VS Build Tools and Windows SDK: replace CBT
   and NuGet, the GFortran Fortran build (Intel `ifx`) and Perl generation
   (native Perl or Python), without MinGW, MSYS2, Cygwin, WSL or Strawberry
   Perl.
2. Prove ABI compatibility with Microsoft MS-MPI 10.1.3 before changing
   behavior.
3. Fix the launch race with a deterministic regression test.
4. Decide file-version identity, signing and licence notices (suite gap
   G20), app-local runtime layout, and launcher/service behavior without an
   installer.
5. Requalify PETSc, its dependencies and SESKA against this fork's SDK and
   runtime before adoption.

- `native/toolchain-pins.json`: the PETSc fork's verified VS Build Tools
  17.14.37411.7 (toolset 14.44.35207), Windows SDK 10.0.26100.0 and Intel ifx
  2026.1.1 entries, byte-identical, with provenance (petsc-native-windows

  928cf7c6cf59b651710ea0a556f649c5e56b35f363b733d911f1922eb59cf3d2), plus
  Microsoft MS-MPI 10.1.3 runtime/SDK as the phase-4 parity reference.
- `native/environment.py`: captures vcvars64.bat plus Intel setvars.bat,
  strips Cygwin/MSYS/MinGW/Strawberry/Git-usr paths and compiler overrides,
  and verifies the VS instance, toolset, SDK, installed-file hashes and tool
  locations (cl, link, lib, dumpbin, midl, mc, rc, ifx, MSBuild). It removes
  NoDefaultCurrentDirectoryInExePath only for the vendor-script session:
  Intel setvars.bat calls component vars.bat by relative name, and with that
  variable set every component fails while setvars still exits 0. It fails
  with a specific error when ONEAPI_ROOT/CMPLR_ROOT are absent. Verified in a
  shell that sets the variable: all tools resolve inside the pinned installs;
  cl.exe SHA-256 88c8344236a27a6e727e0a8edc49aaa2690bdc7a9464b9d18cc7abe70a9f1c0d
  equals the PETSc pin.
- `Directory.Build.props`: the CBT import is skipped when MSMPI_NATIVE=true,
  so a native build loads no CBT.Core.dll and restores no NuGet modules.
  Without the property, upstream behavior is unchanged.
- `native/build.py baseline`: expands upstream dirs.proj into 22 projects and
  builds each with MSBuild global properties MSMPI_NATIVE=true,
  Configuration=Release, Platform=x64, PlatformToolset=v143,
  VCToolsVersion=14.44.35207, WindowsTargetPlatformVersion=10.0.26100.0.
  It continues after failures and writes out/native-baseline/<UTC>/summary.json.
- `native/tests/test_environment.py`: 3 tests pass (vendor-session guard,
  excluded-path filtering, traversal order).

Baseline 20261016T211234Z: 8 of 22 projects built (binplace, launchSvc MC,
traceManifest, mpi_debugger, mpiio, pmicli, pmilib, mpistub). All 14 failures
trace to four missing generated inputs, not to source incompatibility with
the modern toolset:

1. defmsg.h: the Perl extracterrmsgs step did not run; upstream ignores its
   exit code. Port extracterrmsgs and parse.sub (799 and 228 lines) to Python
   and verify against message strings in Microsoft's msmpi.dll 10.1.3.
2. MpiTraceEvents.h (and the launch-service message header): traceManifest
   and msmpiLaunchSvcMc use PlatformToolset WindowsUserModeDriver10.0 (the
   WDK toolset that supplies MessageCompile). The global v143 override
   skipped the step and the project still exited 0. The driver will run the
   pinned SDK mc.exe directly (-um -p Trace -P EVENT_ -z MpiTraceEvents -h/-r),
   so no WDK is needed.
3. setbotf.f: mingw-w64 gfortran is excluded. It defines MPIRINITF and the
   common blocks MPIPRIV1, MPIPRIV2, MPIFCMB5, MPIFCMB9 and MPIPRIVC, and calls
   MPIRINITC/MPIRINITC2 with CHARACTER arguments. Compile it with ifx so that
   lowercase undecorated names, common-block sizes and trailing hidden
   lengths match gfortran -fno-underscoring, with no Intel default-library
   directives.
4. amd64.{cdecl,stdcall}: upstream echoes an empty C file into a not-yet-
   created x64\Release directory and runs the internal aliasobj, both with
   IgnoreExitCode. Gate those targets off natively and emit the COFF alias
   objects (weak externals, IMAGE_WEAK_EXTERN_SEARCH_ALIAS) from the .alias
   files with a Python writer; check parity against Microsoft's msmpifec.lib.

Generators, run by native/build.py before MSBuild:
- Message compiler: the pinned SDK mc.exe 10.0.26100.0 replaces the WDK

- Error catalog: native/extracterrmsgs.py, a faithful Python port of
  extracterrmsgs and parse.sub (Perl-on-Windows CRLF layers, readdir order,
  greedy quote extraction, the trailing-digit routine fallback, the 200-step
  balanced-paren limit, // comment truncation). It runs with the upstream
  arguments and working directory, and any ": error :" diagnostic fails it,
  where upstream ignored the exit code. Result: 330 files, 646 names, 607
  keys, 0 errors; defmsg.h 142,969 bytes; errtest.c (not compiled).
  Independent check, native/check_errmsgs.py against Microsoft msmpi.dll
  10.1.3 (SHA-256 d8f74689e83d7e5a7277de15b221edea91f529529f8a16fd0e510236c0705dcb):
  all 607 keys and all 606 non-empty long formats appear verbatim. Two
  explained exceptions: "**fail" has an empty format, which cannot be
  located by content, and "**user" is a direct literal in errutil.cpp, not a
  catalog key.
- Fortran alias objects: native/aliasobj.py replaces the Microsoft-internal
  aliasobj. Like upstream, plain `cl.exe -c` compiles an empty C file; the
  tool then appends, per `alias <name> <target>` line, an external undefined
  target and a weak external with one aux record (tag index = target,
  characteristics IMAGE_WEAK_EXTERN_SEARCH_ALIAS). That matches the symbol
  pattern dumped from Microsoft's msmpifec.lib member obj\amd64\amd64.cdecl.obj.
- setbotf.f: the pinned ifx (`/nologo /c /Od /names:lowercase
  /assume:nounderscore /libdir:none`) replaces gfortran -fno-underscoring;
  mpifort.vcxproj creates $(O) first. Symbol and common-block parity with
  Microsoft's objects is a phase-4 check.
- Pinned NuGet input: NetworkDirect 2.0.1 (ndsupport.h and others, plus a
  prebuilt ndutil.lib), referenced by mpichannels, mpid and msmpi. It is
  verified against nuget.org's catalog SHA-512 (native/package-pins.json) and

  ForceImportBeforeCppTargets. Follow-up: build ndutil from source.
- Gated upstream steps, unchanged without MSMPI_NATIVE: the CBT import,

Drift found against Microsoft 10.1.3 (to restore for ABI parity in phase 4):
- The 10.1.3 SDK mpi.h adds MPI_Aint_add, PMPI_Aint_add, MPI_Aint_diff and
  PMPI_Aint_diff (MPI-3.1). The source has none of them. Microsoft's
  amd64.cdecl alias object carries 2,508 aliases against the source's
  2,494; the 14 extra are the Fortran MPI_AINT_ADD/MPI_AINT_DIFF names.
  msmpi.dll exports also differ (the Aint family; MPIR_debug_gate and
  MPIR_dll_name need an exact export diff).
- mpif.h, mpi.f90 and mpio.h are identical to the 10.1.3 SDK. pmidbg.h
  differs only in its comment header. mspms.h differs only by the
  source's guarded MinGW compatibility block.
