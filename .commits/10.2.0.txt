Defect Driving The Fork
=======================

- Launch race (Observed): SESKA backend hosted run 38937044789,
  `windows (opt)`, case `displacement-4-mumps`. With `mpiexec -debug 3`, the
  manager logs `ERROR: rejecting unknown process id 3 trying to connect.`
  right after `CreateProcess` of rank 0 (`PMI_SMPD_KEY=3`). The job is then
  aborted ("process exited without calling init"); RPC 1726 on teardown is
  only a consequence.
- Source: `gle_create_mpi_process()` calls `ResumeThread(pi.hThread)`
  (`src/mpi/smpd/smpd_launch_process.cpp:868`) and only after it returns
  does the launch loop call `smpd_add_process(process)` (`:1338`). A rank
  that reaches its PMI connect in that window fails
  `smpd_find_process_by_id()` (`src/mpi/pmilib/SmpdMgrRpcSrv.cpp:439-445`).
- Conditions: oversubscribed two-vCPU Windows Server 2022 runners, where
  the launching thread competes with already-started ranks that busy-poll in
  `MPI_Init`. 600 launches on a Windows 11 desktop (2 and 1 CPUs, 4 and 8
  ranks, busy loops) did not reproduce it; a Server-like long-quantum A/B
  test is in progress in the suite.
- Staged remedy chosen by the user: (1) below-normal rank priority in the
  SESKA launcher and CI now; (2) fix the ordering here (register before
  resume), with a deterministic regression test, and ship this fork's runtime
  app-locally.

Phase 5: launch-race fix and deterministic regression test
==========================================================

Version progression: none (10.2.0.0; counter 0 -> 0). Acceptance requires
the full declared checks and downstream requalification.

- src/mpi/smpd/smpd_launch_process.cpp: gle_create_mpi_process() no longer
  calls ResumeThread. It reports through *pResumeAfterRegistration whether the
  caller must resume (false when a PMI debugger extension requested
  suspension). The launch loop calls smpd_add_process() first and only then
  resumes the primary thread, so a rank's PMI connect always finds its
  registration in smpd_find_process_by_id(). A ResumeThread failure now kills
  the launch block with an error; upstream ignored the return value.
- A test-only block (#if MSMPI_NATIVE_LAUNCH_TEST, never in shipped builds)
  reads MSMPI_NATIVE_TEST_RESUME_DELAY_MS and MSMPI_NATIVE_TEST_LEGACY_ORDER.
- native/verify.py builds that variant as Release in a disposable copy of the
  source tree and runs it with the release mpiexec.exe and msmpi.dll.
  Run out/native-verify/20261016T220621Z: 11 of 11 checks pass.
  Fixed order, 5 four-rank launches with a 300 ms post-resume delay: all exit
  0, with no rejection. Sensitivity control, legacy order with the same
  delay: 3 of 3 launches fail with "ERROR: rejecting unknown process id N
  trying to connect.", reproducing hosted run 38937044789 deterministically.
- Found: the Debug configuration's smpd.exe fail-fasts at startup
  (0xC0000409). Release is unaffected. Investigate before supporting Debug.
